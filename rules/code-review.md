# 🔎 コードレビュールール

## 🎯 このルールが起動する条件

以下のキーワードを含むリクエストで起動します：

- 「レビューして」「コードレビュー」「コードを確認して」
- 「チェックして」「問題ないか見て」「バグがないか確認して」
- 「改善点を教えて」「最適化できる箇所は？」
- 「セキュリティ的に問題ないか」「テストは十分か」

---

## 📋 レビュープロセス

### STEP 1：コンテキストの理解

コードを批評する前に、必ず理解フェーズを実施する：

```
<thinking>
コンテキスト理解チェック：
□ このコードは何をするものか理解できたか？
□ 関連するファイルや依存関係を確認したか？
□ なぜこう書かれているか（意図・背景）を把握したか？
□ テストファイルが存在する場合は確認したか？
□ プロジェクトの言語・フレームワーク・規約を確認したか？
</thinking>
```

### STEP 2：重要度分類

発見した問題を以下の3段階で分類する：

| 重要度 | 意味 | 対応方針 |
|---|---|---|
| 🔴 **Critical（致命的）** | バグ・セキュリティ脆弱性・データ損失リスク | マージ前に必ず修正 |
| 🟡 **Important（重要）** | パフォーマンス問題・エラーハンドリング不備・論理問題 | 今スプリントで対処推奨 |
| 🟢 **Suggestion（提案）** | 可読性・命名・スタイル・簡略化の機会 | 機会があれば対処 |

### STEP 3：具体的なフィードバック

すべてのフィードバックに以下の3点を含める：

1. **何が問題か**（事実の記述）
2. **なぜ問題か**（影響・リスクの説明）
3. **どう直すか**（具体的な修正案・コードスニペット）

## 🔍 チェック観点

### 1. 正確性（Correctness）

- ロジックエラーとオフバイワン
- 未処理のエッジケース（None/null、空文字、境界値）
- 並行処理でのレースコンディション
- データ型・APIコントラクトの誤った前提

**Python固有チェック：**
```python
# ❌ 可変なデフォルト引数（典型的なPythonバグ）
def add_item(item, items=[]):
    items.append(item)
    return items

# ✅ 正しい書き方
def add_item(item: str, items: list[str] | None = None) -> list[str]:
    if items is None:
        items = []
    items.append(item)
    return items
```

---

### 2. セキュリティ（Security）

- サニタイズされていないユーザー入力（SQLインジェクション・XSS・コマンドインジェクション）
- ハードコードされた認証情報・シークレット
- 認証・認可チェックの欠落
- 安全でないデータ処理（機密データのログ出力・弱い暗号化）

**Python固有チェック：**
```python
# ❌ SQLインジェクション脆弱性
query = f"SELECT * FROM users WHERE name = '{user_input}'"

# ✅ パラメータ化クエリ
query = "SELECT * FROM users WHERE name = %s"
cursor.execute(query, (user_input,))

# ❌ ハードコードされた認証情報
API_KEY = "sk-1234567890abcdef"

# ✅ 環境変数から取得
import os
API_KEY = os.environ["API_KEY"]
```

---

### 3. パフォーマンス（Performance）

- ループ内の不要な処理（N+1クエリ・繰り返し計算）
- キャッシュ機会の見逃し
- 大きなメモリ確保・リーク
- 非同期化すべきブロッキング処理

**Python固有チェック：**
```python
# ❌ リスト内包表記の代わりにforループ（パフォーマンス）
result = []
for item in items:
    result.append(item * 2)

# ✅ リスト内包表記
result = [item * 2 for item in items]

# ❌ ループ内でのDB問い合わせ（N+1）
for user in users:
    orders = db.query(f"SELECT * FROM orders WHERE user_id = {user.id}")

# ✅ JOINまたはIN句でまとめて取得
orders = db.query("SELECT * FROM orders WHERE user_id IN (%s)", user_ids)
```

---

### 4. 保守性（Maintainability）

- 責務が多すぎる関数・クラス（単一責任原則違反）
- 重複ロジック（DRY原則違反）
- 不明確な命名・コンテキスト不足
- デッドコード・未使用インポート

---

### 5. エラーハンドリング（Error Handling）

- ログを残さない例外の握りつぶし
- I/O操作のエラーハンドリング欠落
- デバッグに役立たないエラーメッセージ
- 失敗パスでのクリーンアップ処理の欠落

```python
# ❌ 例外の握りつぶし
try:
    result = process_data(data)
except Exception:
    pass

# ✅ 適切なログと再raise
import logging
logger = logging.getLogger(__name__)

try:
    result = process_data(data)
except ValueError as e:
    logger.error("データ処理失敗: %s", e)
    raise
```

---

### 6. テストカバレッジ（Testing）

- テストが書かれているか
- ハッピーパスだけでなくエラーパス・エッジケースがあるか
- テストが独立しているか（実行順序に依存しない）
- モックが適切に使われているか

---

### 7. Python固有の品質チェック

- 型アノテーションが付いているか（PEP 484）
- docstringが適切か（Google Style推奨）
- `__init__.py` の構成は適切か
- `pathlib.Path` vs `os.path`（Pathlib推奨）
- f-string vs `format()` vs `%` の一貫性
