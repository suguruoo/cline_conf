# コードレビューのチェックリスト

レビューでは、まず機械検査を実行し、その結果に加えて以下をレビューする。
指摘は規約の項番 (coding-standards.md) を添えて、重大度順に報告する。

## 手順

1. `python3 <S>/check_python.py <対象> --plan <plan.md> --root <ワークスペース>` を実行する (`<S>` = この skill の scripts)。
   plan.md が無い単純なレビューでは `--no-modules` を付け、使用モジュールの承認状況はレビューで確認する。
2. ERROR は全て指摘する。WARN は推奨・例外として判断し、例外にするなら理由が書かれているか確認する。
3. 下記のレビュー項目を、差分と周辺コードを読んで確認する。
4. 指摘は次の形で報告する:

```
[重大度: high|medium|low] 規約 N / 箇所: path:line
問題: …
根拠: …
修正案: …
```

## 機械検査では分からない項目

| 規約 | 確認すること |
|---|---|
| 1 | 新しく import されたモジュールは、承認済みの表にあるか。選定理由と代替案は妥当か |
| 6 | プライベートにすべきものが公開されていないか (`_` / `__` の使い分け) |
| 7 | 名前だけで機能が分かるか。略語・汎用語 (`data` `info` `handle`) に頼っていないか |
| 8〜10 | docstring の内容が実装と一致しているか。Raises に実際の例外が全て書かれているか。公開 API に Example (doctest) があるか |
| 17〜18 | 例外クラスは具体的か。握りつぶし (`except X: pass`) がないか。独自例外が必要な場所で汎用例外を使っていないか |
| 19〜20 | テストは正常系・異常系・境界を押さえているか。テスト名が条件と期待結果を表しているか |
| 21〜23 | ログレベルは適切か。機密情報 (パスワード・トークン・個人情報) をログに出していないか。例外時に `exc_info=True` があるか |
| 24〜25 | コメントは「なぜ」を書いているか。コードの言い換えコメントがないか。TODO に担当・期限/Issue があるか |
| 26 | マジックナンバー・グローバル変数の例外には理由があるか |
| 28 | 規約から逸脱した最適化には、PERFORMANCE OPTIMIZATION の注記と根拠があるか |

## 一般的な観点 (規約外だが毎回見る)

- 要件 (spec の AC) を満たしているか。範囲外の変更が混ざっていないか。
- 入力検証・境界条件・失敗時の挙動。
- セキュリティ (インジェクション、秘密情報のハードコード、権限)。
- 性能 (N+1、不要な全件読み込み)。

## TypeScript

プロジェクトの ESLint + Prettier 設定が優先。`npx --yes eslint .` と `npx --yes prettier --check .` を実行し、結果を報告に含める。
設定が無い場合は、その旨を指摘する (勝手に設定を追加しない)。
