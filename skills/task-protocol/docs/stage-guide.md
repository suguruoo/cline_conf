# 段階ごとの書き方ガイド

## spec

目的は「何を作るか」ではなく「何が満たされたら成功か」を固定すること。plan 以降はこの spec が基準になる。

- 目的: 用途と読者・利用者。意思決定に使うなら、何の決定か。
- スコープ / 非目標: 非目標を書くと、後の逸脱判定が楽になる。
- 受け入れ条件 (AC):
  - 悪い例: `- AC1: 見やすいレポートになっている`
  - 良い例: `- AC1: lint_report.py がエラー 0 で終了する ｜検証: 終了コード 0`
  - 数は 3〜7 個が目安。多すぎる場合はスコープを分割する。
- 未確定事項: 推測で埋めずに質問として書く。ユーザーの回答を得たら `- [x]` にして回答を併記する。

## plan

- 方針: 選んだ理由と、検討した代替案を 1〜2 行。
- ステップ: 1 ステップ = 1 回の作業単位で、完了を証拠で示せる粒度。最後のステップに検証を含める。
- リスクと手戻り点: 「X が取得できない場合は spec の Q2 を『判断不能』にして続行」のように、戻り先まで書く。

## progress

- 1 ステップ終えるごとに更新する (まとめて後で書かない)。
- evidence の例: `evidence: tasks/<id>/sources/3.txt; cmd: python3 lint_report.py ... => exit 0`
- 逸脱が必要な場面の例: plan に無い調査対象が必要になった / AC を満たすために方針を変える / 外部の制約でステップが実行できない。
  - 起票 → 作業停止 → 人間が `taskctl approve D1` → 再開。
  - 承認前にその逸脱に基づく作業を進めない。

## result

- サマリは「何ができたか・どこにあるか」。経緯の説明は不要。
- 判定の根拠はファイルパスかコマンド結果。「確認した」だけは不可。
- waived は、AC を満たさないが受け入れる場合のみ。理由を書き、承認時に人間が判断する。
- 残課題・限界: 無いなら「なし」と明記する。
